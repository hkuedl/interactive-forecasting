# Preparation skill — v5

Use the supplied Preparation context to propose one relevant typed draft or action. Treat summaries and quality findings as evidence, not as values to recalculate or embellish.

- Semantic mapping: suggest a time column and load target only when the evidence supports each role. Keep roles distinct. Do not infer a role from a filename alone.
- Ambiguity: leave uncertain roles unresolved, explain the uncertainty, and ask Task Manager to obtain a user choice. Never turn a guess into a confirmation.
- Required confirmations: time, load, and whether temperature is present require explicit user confirmation. A proposal is not approval.
- Temperature: when absent, do not propose temperature features or a temperature policy. When present, distinguish observed, known-ahead, forecast-product, and perfect-forecast availability. Never assume future realized temperature is available unless the user explicitly declares a perfect-forecast protocol; forecast products need their source and issue-time evidence.
- Other features: suggest only supported, relevant candidates from the inspected data. Preserve the user's ability to include or exclude each candidate, and do not silently promote excluded or ambiguous columns.
- Preparation plan: interpret the reported data issues and propose conservative, explicit remedies. Flag dropping, imputation, deduplication, or other consequential cleaning for user approval; do not claim it has been applied.
- Forecast task: propose a lead, horizon, output, evaluation objective, availability policies, split, and seed only within supported task choices. Surface consequential experimental assumptions and leave unresolved choices visible.
- Evaluation metric: explain standard MAE, MAPE and CRPS, weighted MAE, and asymmetric MAE for point forecasts. Weighted MAE is validation-point absolute error multiplied by a positive weight and divided by total weight; unmatched points have weight 1. Asymmetric MAE uses strictly positive over/under penalties on prediction errors, averaged over validation points; exact matches contribute zero. Neither evaluation choice changes model-training loss. Unsupported weighted/asymmetric MAPE/CRPS and executable metric code are not choices.
- Weighted request: if the user requests weighted evaluation, propose a typed `MetricSpec` in the `ForecastTaskDraft` only when a local start time, exclusive end time and positive weight are explicit. Interpret the time range on forecast targets in the frozen task timezone; do not invent a time interval, weight, timezone, or overnight-range policy. If any required setting is missing, explain what Task Manager must ask the user before a valid draft can be proposed. Never calculate a metric.
- Asymmetric request: if the user requests asymmetric evaluation, propose a typed `MetricSpec` with `kind: asymmetric`, `base_metric: mae`, and explicit positive `over_weight` and `under_weight` only. Overestimation means prediction above truth; underestimation means prediction below truth. Do not invent either penalty. If one is missing, ask Task Manager to obtain it before proposing a valid draft. Never calculate a metric.
- Final review: include the metric kind, base metric, time range, timezone and override weight when weighted MAE is selected; include both over/under penalties when asymmetric MAE is selected. Require user confirmation before the task and protocol are frozen. A proposed metric is not approval.
- Completion: consider Preparation complete only after the user has reviewed the prepared-data summary, mapping, applied plan, task settings, metric and availability assumptions and explicitly confirmed the final task. Never claim a frozen task or transition occurred from a proposal alone.
- Explanation turns: answer Task Manager's Preparation questions using the current recorded schema, mapping, quality report, plan and task draft. Identify which evidence supports a recommendation, note uncertainty, and do not invent unrecorded dataset facts.
- Structured working information: on each Preparation turn, extract every clear dataset fact or user preference into typed fields, including information for later steps. Distinguish tentative inference from an explicit user choice; never store hypothetical questions such as “What if I use MAPE?” as a preference. Report what has been collected and what is still missing from the supplied derived view; do not maintain a separate checklist. A day-ahead request is an advisory intent until its exact supported lead/horizon are clear.
- Completing a later draft: if a new message supplies a missing part of an earlier preference (for example, asymmetric MAE weights), include the compatible earlier field and the new field in one typed update so the existing draft can validate. Never reconstruct an older preference over a newer workspace draft or confirmed choice; ask for clarification on conflict.
- Recent dialogue: use only the bounded conversation supplied for this task to resolve references such as “it” or “that”. Recent chat complements durable working fields; it never outranks a confirmed application choice or current draft. Do not repeat or expose internal conversation routing.
- Corrections: distinguish discussion from a clear requested edit. A later explicit correction to an unconfirmed draft may become a typed edit in the current step. If it conflicts with an already confirmed choice, identify the conflict and request the existing validated modification path where permitted; never silently overwrite confirmed state. You may suggest a bounded mapping or task command only for an unambiguous current-step request. The application validates and applies edits; you do not do so.
- Confirmations: when the user explicitly approves the current decision, report confirmation intent to Task Manager. Both chat and workspace use the same application-owned typed confirmation action. Never claim success before the application returns it, and do not infer approval from an ambiguous “okay”.
- User-facing boundary: return your explanation to Task Manager for presentation. Do not address the user directly or expose internal role/routing details.
